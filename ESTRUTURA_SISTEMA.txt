ESTRUTURA DO SISTEMA - MONITORAMENTO DE RESERVATORIOS
=====================================================

1) VISAO GERAL
--------------
O sistema possui 3 camadas principais:

- Entrada de dados (API ESP32)
- Regra de negocio (models + services)
- Apresentacao (views + templates)

Fluxo principal:
ESP32 -> POST /api/esp32/leituras/ -> processar_leitura_esp32 ->
calcular_status -> salva LeituraQualidade -> atualiza status do ponto ->
sincroniza status do reservatorio pelo ponto unico.


2) ESTRUTURA DE PASTAS
----------------------
setup/
- settings.py: configuracoes Django (token, hosts, static, etc.)
- urls.py: roteamento principal

app/
- models.py: entidades de dominio
- views.py: entrada HTTP e renderizacao de telas
- services/
  - ingestao.py: orquestra ingestao da ESP32
  - regras.py: regras de classificacao de status
- templates/
  - index.html: listagem de reservatorios
  - reservatorio/detalhe.html: painel detalhado com graficos
  - reservatorio/calibracao*.html: fluxo de calibracao do ponto unico
  - auth/entrar.html: tela de login
  - blocos/: layout base, navbar e footer
- static/
  - css/: estilos da aplicacao
  - js/reservatorio-detalhe.js: logica dos graficos do detalhe/relatorio
- tests.py: testes de login, CRUD, calibracao e ingestao


3) MODELO DE DADOS
------------------
Reservatorio
- dono (usuario)
- nome
- status (status geral)
- regra: status geral = status do ponto unico

PontoMonitoramento
- pertence a um reservatorio
- tipo canonico: ponto_unico
- compatibilidade de entrada: antes_tratamento | depois_tratamento | pre | pos
- status_atual: status da ultima leitura do ponto

LeituraQualidade
- pertence a um ponto
- dados finais: temperatura, tds, turbidez, ph
- sinais_brutos: ADCs, timestamps de firmware, device_id
- status_leitura: status calculado na criacao da leitura


4) REGRAS DE STATUS
-------------------
Arquivo: app/services/regras.py

- perigo: desvio critico em qualquer metrica
- atencao: desvio moderado em qualquer metrica
- bom: todas metricas dentro da faixa

Observacao:
- o frontend e o dashboard agora exibem apenas o ponto unico.


5) RESPONSABILIDADES
--------------------
Views:
- validam request HTTP
- delegam regra para services/models
- retornam redirect/render/json

Services:
- coordenam fluxo de ingestao
- validam payload e dados obrigatorios

Models:
- concentram regra de dominio e estado
- metodos principais:
  - Reservatorio.sincronizar_status_pelo_ponto
  - PontoMonitoramento.registrar_leitura


6) COMPATIBILIDADE LEGADA
-------------------------
- A aplicacao web trabalha apenas com ponto unico.
- A API ainda aceita ponto_tipo legado para nao quebrar a biblioteca Arduino atual.
- O repositorio MonitoramentoAgua nao foi alterado nesta etapa.


7) PONTOS DE ATENCAO PARA EVOLUCAO
----------------------------------
- Se a biblioteca Arduino migrar depois para ponto_unico, a compatibilidade legada pode ser simplificada.
- Para API externa, considerar endpoint dedicado em modulo separado (app/api/).
- Para producao, sempre configurar DJANGO_SECRET_KEY e ESP32_API_TOKEN via variavel de ambiente.
